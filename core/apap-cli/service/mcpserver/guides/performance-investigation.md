# Performance Investigation Pathway

For multi-step investigations, follow this loop within the user's requested scope. The aim is to gather evidence to establish the root cause of a performance issue:

1. **Clarify the goal.** Establish the following using information already supplied. Ask for material missing details together, then await answers before workload-specific investigation or source code changes:
    - Workload, application or system scope, including workload parameters if relevant
    - Profiling target
    - Success metric: which aspect of performance should improve, such as elapsed time for a defined workload, throughput or latency
    - Correctness constraints or business logic to be preserved in the workload or on the system
2. **Choose relevant measurements.** Follow the recipe-selection guidance in the server instructions and briefly explain how the recipe answers the current question.
3. **Establish a baseline.** Obtain an original Performix run before making optimization changes. Before reusing any run, check its recorded metadata against the planned validation: CPU model and core count, memory, OS/kernel, source/build, inputs, concurrency, load and collection settings. An existing run that meets these checks may be reused without reprofiling. If material differences or missing information make it unsuitable, use it only as investigation context and profile the original workload on the validation target under the planned conditions. If a suitable baseline cannot be obtained, report that limitation.
4. **Check evidence quality.** Inspect run completion, coverage and competing activity. Leftover workloads, builds or unrelated jobs can contaminate profiles and timings. Repeat contaminated or unrepresentative comparisons under controlled, representative conditions; report limitations if trustworthy evidence remains unavailable.
5. **Follow the evidence.** Treat generated insights and source-based explanations as hypotheses. Use initial profiles to locate costly work, then collect focused Performix evidence to test the suspected mechanism at the relevant function, call path or system resource. Follow the recipe-selection guidance in the server instructions to select measurements that distinguish the plausible causes.

   Tie causal claims to specific run data and account for measurement limitations. A measured speedup establishes the change's effect, but does not automatically establish its proposed explanation.

   Do not treat reaching a runtime or throughput threshold as completing a requested diagnosis while its evidence requirements remain unmet. If evidence remains insufficient, label the explanation as a hypothesis and identify the next useful measurement. Stop when the user's diagnostic and performance goals are met, or explain why no useful further experiment is supported.
6. **Isolate experiments and preserve required work.** Test individual optimizations or a coherent group against the baseline. Isolate changes when needed to support claims about an individual change's effect. Preserve the benchmark's required measured work; matching outputs alone do not establish an equivalent performance comparison. Caching or reducing computation is valid only when permitted by the workload constraints.
7. **Verify correctness.** Compare the original and changed implementations on identical inputs and equal completed work using a separate functional check appropriate to the correctness constraints. Ensure the check can detect differences in the changed computation: compare relevant component or per-iteration results, or use an aggregate that preserves differences. Matching results from timed runs with different completed work do not establish correctness. Keep functional-check changes separate from the performance benchmark. If correctness cannot be established, report that limitation rather than claiming validation.

8. **Measure performance benefit.** Re-run the relevant Performix recipe under the baseline conditions apart from the intended change, and measure the success metric with the same repeatable method. Repeat success-metric measurements for both baseline and changed versions; compare representative values and observed variation rather than selecting the best results. Increase repetitions when variability makes the improvement uncertain or prevents determining whether a user-specified target has been met. If the evidence remains inconclusive, report that limitation instead of claiming a validated optimization.

   Check that profiling coverage and sample counts support the diagnosis, repeating collection when findings are unstable or undersampled. Changes in relative profiling metrics, such as hotspot sample shares or bottleneck percentages, do not by themselves demonstrate improved workload performance. Confirm any improvement using the chosen success metric, such as elapsed time, throughput or latency.

9. **Summarize the investigation.** Briefly report the steps taken, recipe choices, run IDs, changes tested, correctness checks, before/after measurements, repetition counts and observed variation, and conclusions. Distinguish measured findings from hypotheses, citing the relevant run IDs and supporting metrics, and disclose material evidence gaps.
